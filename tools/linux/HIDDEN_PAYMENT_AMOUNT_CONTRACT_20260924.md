# 수금 비공개 금액 계약 및 정산 보존 검증

## 범위와 영향

사용자 정책은 금액 조회 권한 없이 품목·수량·비고 저장 허용, 금액은 서버 계산이다. 기존 전표 금액 계약을 서버 읽기 응답에 연결하기 전, 전표에 중첩되거나 별도 동기화되는 수금 금액이 필수 숫자인 문제를 확인했다. 비공개 값을 0원으로 보내면 연결 전표와 렌탈 정산을 바꿀 수 있으므로 로컬 수정 진행 가능으로 판단했다.

PaymentDto.Amount는 명시적 null을 허용한다. 기존 실제 0원 기본값 및 공개 숫자 형식은 유지한다. 로컬 Payment에는 AmountsHidden 상태를 추가하고 SQLite 이전 자료의 금액·dirty·revision을 유지하며 열을 추가한다. 매핑은 숨김 상태를 왕복 보존한다. 활성 수금이 비공개면 부모 전표의 목록·상세·판매 편집·금액 문서 출력도 비공개로 취급한다. 삭제된 이력은 제외한다.

서버 직접 저장 및 동기화는 비공개 수금의 신규·수정을 거부한다. 삭제 전달은 서버의 기존 금액을 보존한다. 전표 품목·수량·비고의 서버 계산 저장 정책은 그대로 유지하며, 이 변경이 수금액을 임의로 계산해 신규 수금을 허용하는 것은 아니다.

로컬 동기화는 숨겨진 수금을 0원으로 사용해 연결 거래를 삭제하거나 정산액을 바꾸지 않는다. 거래만 내려오는 역방향 투영도 비공개 수금과 해당 revision을 보존한다. 금액이 확인되는 수금 응답을 다시 받으면 공개 상태로 갱신된다. 수정 대기 수금과 기존 렌탈 정산 요약은 보존한다. 업체/지점·자산·품목 범위나 운영 DB는 바꾸지 않았다.

- 데스크톱 관련 133건 통과. General/Web JSON 명시적 null, 실제0원, SQLite 재연결·구형 열 추가, USENET/YEONSU/ITWORLD 수금·연결 거래·dirty 보존, 렌탈 정산 및 기존 출력 권한 취소를 포함한다.
- 최초 데스크톱 집중검사 4건 실패는 새 시험이 캐시된 공용 AppPaths DB를 사용한 원인이었다. 시험별 명시적 SQLite 파일로 수정하고 최종133건을 통과했다. 최초 실패 로그도 보존했다.

## 남은 작업
