# 품목·등급·렌탈 금액 응답 및 호환성 진단 — 2026-09-24

## 결론

현재 로컬 빌드의 품목·등급·렌탈 응답은 금액 권한에 따른 서버 마스킹이 미완료다. 화면에서 금액을 가려도 응답과 동기화 캐시에 원금액이 남는다. 숫자를 즉시 null로 바꾸는 것도 안전하지 않다. 6종 DTO의 금액 속성 16개가 null 역직렬화를 모두 거부했다. 서버와 PC/모바일 소비자, 이전 버전 차단을 함께 변경해야 한다.

이번 작업은 진단이며 이 결함의 수정을 완료한 것이 아니다. 운영 서버의 현상을 직접 확인했다는 주장도 아니다. 현재 소스에 대응하는 로컬 서버 DLL을 사용했고 운영 서비스·업무 DB·공식 테스트 실행 파일은 변경하지 않았다.

## 실제 확인한 호환성 문제

`ItemDto` 가격 6개, `ItemPriceGradeDto.UnitPrice`, `RentalAssetDto` 가격/월요금 3개, `RentalBillingProfileDto` 금액 4개, `RentalBillingLogDto.BilledAmount`, `RentalAssetAssignmentHistoryDto.MonthlyFee`의 null 역직렬화가 실패한다.

PC `LocalMappings`는 이 값들을 그대로 숫자 필드에 저장하고 다시 DTO로 돌린다. 단순 `?? 0` 보정은 비공개와 실제 0원을 구분하지 못하며 재전송 때 0원으로 바뀔 위험이 있다. 모바일 품목 편집도 원본 금액이 없으면 현재 `?? 0`으로 보정하는 경로가 있다. 서버 가격 보호는 유지하되, 클라이언트가 숨김 상태를 명시적으로 저장하고 출력·계산·재전송에서 이를 지켜야 한다.

렌탈의 `DepositText`, `BillingTemplateJson`, `BillingRunsJson`도 금액 경로다. 상위 숫자 필드만 null로 바꿔서는 보호되지 않는다. 업무 메모 전체를 지우거나 숫자 정규식으로 삭제하는 방식은 수량·날짜·업무 설명을 손상하므로 사용하지 않는다.

현재 프로토콜 2는 nullable **전표** 금액을 지원한다는 의미다. 같은 버전이 품목·등급·렌탈까지 처리할 수 있다고 간주하면 안 된다. 새 소비자가 완성된 뒤 명시적인 새 capability/protocol과 해당 응답 경로를 포함하는 426 차단이 필요하다.

## 다음 구현 순서와 완료 조건

1. 품목/등급의 nullable 계약과 방향별 숨김 상태를 PC·모바일 캐시/편집/출력에 연결한다. 신규/기존/dirty/삭제/충돌/재전송을 모두 검증한다. `null`은 서버가 계산하거나 기존 값을 보존해야 하며 실제 0원 입력과 구별한다.
2. 렌탈 프로필·자산·이력·로그 및 구조화 JSON을 같은 방식으로 바꾼다. 자산 소유권, 품목 원본 수정 권한, 청구 주체, 업체/지점 조회 범위를 서로 혼동하지 않는다.
3. 서버의 목록·상세·저장·재전송·일반/렌탈 Pull·충돌 응답에 권한별 투영을 연결한다. DB 원본과 감사 원본은 변경하지 않는다. 기존 Transaction Pull 마스킹과 함께 소비자 준비 상태를 검증한다.
4. 구버전/헤더 없음/새 capability, 로그인 전환·권한 회수·오프라인 편집 후 재접속, 제한 계정의 품목·수량·비고 저장과 서버 금액 계산을 실제 흐름으로 확인한다. 실제 0원·비공개·행 없음은 별도로 검증한다.
5. 관련 회귀와 공식 테스트 앱을 다시 확인한 뒤 전체 통합 수정 기준으로 버전·설치/업데이트 파일을 재생성한다. 운영/Git 반영은 기존 완료 기준을 따른다.

금액 보호 외에 기존 업무자료 정합성, 실기기, 독립 복원, 워크플랜의 남은 검증 등 전체 Goal 범위는 그대로 남아 있다.
