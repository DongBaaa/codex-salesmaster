# 전표의 비공개 금액과 실제 0원 구분

## 범위와 사전점검

이전 가격 쓰기 보호 다음 단계다. 사용자는 금액 권한이 없는 직원도 품목·수량·비고를 저장하고 금액은 서버가 계산하도록 결정했다. 기존 decimal DTO는 생략 값을 0으로 읽고 null을 거부했으므로, 읽기 응답 마스킹을 먼저 켜면 PC/모바일 재전송이 안전하지 않았다.

판정: 로컬 계약·저장·재전송 수정은 진행 가능. 기존 tenant/office 및 받은 재고 원본 수정 권한은 변경하지 않는다. 운영 데이터·계정·서비스를 변경하지 않는다. 서버 읽기 응답의 권한별 비공개 적용은 아직 연결하지 않았으며, 이번 결과를 금액 권한 전체 완료로 해석하지 않는다.

## 구현

- InvoiceDto의 합계/공급가/부가세, InvoiceLineDto의 단가/행 금액은 nullable decimal이다. JSON 필드 이름은 기존 이름과 직렬화 naming policy를 유지한다. null 무시 옵션 아래에서도 이 5개 값은 명시적 null로 기록된다. 실제 0은 숫자 0이다.
- 기존 코드가 새 전표를 만들 때의 기본 0은 유지한다. 따라서 필드 자체가 생략된 구형 요청을 비공개로 추정하지 않는다. 비공개는 명시적 null로 전달해야 한다.
- AmountsHidden은 null에서 계산하는 상태이며 JSON에 별도 주장 값으로 저장하지 않는다. 일부 행만 null이어도 PC 경계에서 전표 금액 전체를 비공개로 취급한다.
- PC Invoices/InvoiceLines에 AmountsHidden 열을 추가한다. 기존 숫자 열은 유지하되 숨김 상태의 내부 값은 0, 반드시 함께 저장되는 상태 열은 true다. DTO 변환 시 다시 null로 전송한다. **이 내부 숫자 열을 직접 읽는 기존 화면·집계·인쇄는 아직 별도 대응이 필요하다.** 실제 서버 응답 비공개를 켜기 전 그 경로를 마쳐야 한다.
- 전표 버전 저장과 행 복제는 비공개 상태를 유지한다. 단순 매핑 시험뿐 아니라 실제 LocalStateService 저장 뒤 null 재전송을 확인한다.
- 금액 권한이 있는 사용자에게 비공개 캐시가 남아 있으면 서버가 재조회를 요구하며 저장을 거부한다. 제한 계정의 null 요청은 기존 서버 가격 계산을 거쳐 저장한다. 동일 null 요청 재전송은 기존 mutation 영수증으로 처리한다.
- 서버 영속화 경계는 DisclosedAmount.Require로 계산이 끝나지 않은 null을 0으로 바꾸지 않는다. 구조 변경 비교도 nullable을 보존한다.
- 모바일 초안의 비공개 상태와 재전송 null을 유지한다. 전표 요약/잔액, 관련 렌탈 이력, PDF의 비공개 값을 0원으로 계산/표시하지 않도록 보완했다. 비공개 잔액으로 수금/지급을 새로 저장하는 것은 차단한다. 전체 모바일 입력 화면·목록·권한 전환·실기기 검증은 미완료다.

## 완료 전 필요한 작업

1. 서버 전표 목록/상세/Sync Pull 및 품목·수금·렌탈·잔액·첨부의 권한별 응답을 일관되게 처리한다. 전표 Payments에 포함된 금액도 따로 보호해야 한다. 이번 DTO 변경만으로 현재 서버 금액 노출이 막힌 것은 아니다.
2. PC 화면·집계·출력에서 AmountsHidden을 빠짐없이 처리하고, 권한 변경/계정 전환/오프라인의 기존 금액 캐시 및 dirty 원본을 안전하게 분리한다.
3. 모바일 전체 입력·출력 흐름을 실제 화면으로 검증한다. 이번 null 처리 일부와 컴파일만으로 완료를 판단하지 않는다.
4. 구형 앱에 명시적 호환성 차단 및 업데이트 경로를 연결한다. 구형 decimal 수신기의 실패는 0원 오해를 막는 증거이지, 사용 가능한 업그레이드 안내의 완료 증거가 아니다.
5. 제한 계정 실제 작성·저장·재로그인·재전송 및 관련 회귀 후 통합 패키지를 새로 생성하고 공식 시험/수락/운영 반영을 진행한다. 현재 743 설치 후보 및 기존 Android APK는 이번 수정을 포함하지 않는다.
